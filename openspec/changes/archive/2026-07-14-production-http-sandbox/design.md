## Context

The HTTP executor is a privileged egress capability for plans that may be
generated by an AI system. Exact origin allowlisting prevents arbitrary URL
selection but does not by itself prevent an approved DNS name from resolving to
loopback, link-local, RFC1918, ULA, metadata, or other special-use addresses.
The inbound API server also currently performs protocol detection in the accept
loop and accepts plaintext even when TLS credentials are configured.

The command executor uses Minijail namespaces, Landlock, seccomp, and rlimits.
Minijail's upstream threat model is containment of known binaries, not execution
of malicious binaries. DAGForge therefore has to enforce the known-binary
precondition itself and must not advertise arbitrary-code isolation.

## Decisions

### Inbound HTTP is an explicit transport mode

The server is configured before start as either plaintext or TLS-only. A TLS
listener never auto-downgrades to plaintext. Each accepted socket is dispatched
immediately so a slow client cannot block the accept loop. Handshake and request
idle deadlines, parser limits, active-connection capacity, and maximum requests
per connection are server-owned limits.

### Outbound policy is enforced after DNS resolution

The origin remains an exact scheme/host/port allowlist. The HTTP client filters
resolved endpoints before connect. Special-use/private endpoints are denied by
default; explicit CIDR entries may allow required internal destinations. The
client connects only to retained endpoints, so DNS rebinding cannot substitute
a new address after policy evaluation for the current request.

### TLS policy is server owned

Outbound TLS has a minimum protocol version, system trust by default, an
optional additional CA file, and an optional client certificate/private key
pair.
Partial mTLS configuration is rejected. Redirects remain disabled.

### Command execution is known-binary containment

The adapter requires an exact absolute program allowlist by default. Program
paths are canonicalized and checked for regular executable files before plans
are accepted. Minijail, seccomp BPF, and the workspace root are preflighted when
the executor is created. Writable-by-group/other helper and policy files are
rejected.

The workspace root cannot be a symlink or reside under the system temporary
directory. Per-attempt directories are created with owner-only permissions.
Captured stdout/stderr and pending unterminated stream lines have independent
bounds. Exceeding a bound terminates the process group and reports resource
exhaustion instead of silently truncating while the process continues.

### Application teardown closes execution boundaries first

The control plane stops accepting requests first. Workflow Runtime then enters
quiescing mode, rejects new Runs, cancels every active Run on its owner shard,
waits for Run/Task/executor coroutines to finish, and executes a barrier on each
Runtime shard. Only after that barrier may the command executor kill any
remaining known process groups and Runtime threads stop. HTTP server socket
closure is dispatched on each socket's executor and waits for every connection
handler to unregister.

## Security boundary statement

The 0.4 command sandbox is suitable for approved, administrator-installed
binaries processing untrusted inputs. It is not suitable for binaries supplied
by a Workflow author, self-modifying toolchains, writable shared libraries, or
hostile native code. Those workloads require a stronger isolation class such as
a userspace kernel or microVM and are outside this change.
